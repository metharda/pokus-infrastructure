# pokus-infrastructure

> **Status: pre-release.** No version has been released yet. The lab has not
> been verified end to end on real hosts (`make test-distros` and the
> real-machine tests are still to run), and its interfaces, the platform
> contract and the defaults may still change. Use it only on a machine you
> can rebuild.

Infrastructure-as-code for the Pokus research lab: it turns a Linux machine
into a lab host for benchmarking AI diagnostic agents on reproducible, injected
Linux faults. It provides host checks (preflight), accounts, remote access over
Tailscale, the Incus target sandbox, local model serving with vLLM,
observability, backups, and the `pinka` operator tool. The research
services come from pokus-platform and run on top of it.

The documentation is in `docs/` (MkDocs): start with
[docs/index.md](docs/index.md), or build it into `site/` with `make docs`. On
a lab host, `pinka docs serve` serves it on `127.0.0.1` for offline use.

## Prerequisites

- A machine with one of the environments above, systemd as PID 1, cgroup v2,
  and btrfs or LVM thin provisioning for the target storage pool (preflight
  checks all of it: `./preflight/pinka-preflight --no-write`).
- `git` and `sudo`; bootstrap installs its own pinned Python and Ansible.
- A Tailscale account for the lab's remote access and the researchers' SSH
  public keys.
- For local inference: an NVIDIA GPU with at least 8 GiB of memory (on WSL2
  the Windows driver; on Linux the lab installs a pinned driver).

## Quickstart

Clone the repository and let bootstrap start the installer, which asks for
every setting, writes `ansible/inventory/host_vars/<machine>.yml`, the
researchers' keys and the encrypted vault, and provisions the host:

```bash
git clone <repository-url> pokus-infrastructure
cd pokus-infrastructure
./preflight/pinka-preflight --no-write
sudo ./bootstrap/bootstrap.sh
```

Without a terminal UI, write an answers file and run bootstrap with
`--answers <file> --non-interactive --vault-password-file <file>`: it writes
the host_vars file (from `ansible/inventory/host_vars/example-machine.yml`)
and creates the encrypted vault (shaped like
`ansible/group_vars/all/vault.yml.example`) itself
(`docs/how-to/install-without-the-tui.md`). Every later run is
`sudo ./bootstrap/bootstrap.sh --machine <machine>`, and a run on an
unchanged host changes nothing (`changed=0`). The tutorials
`docs/tutorials/install-wsl2.md` and `docs/tutorials/install-baremetal.md`
walk through a complete installation.

## When something fails

- Bootstrap prints the exit code and the log file
  (`/var/log/pinka-bootstrap/<UTC>.log`); `docs/how-to/troubleshoot.md` has a
  section per code.
- On a provisioned host, `sudo pinka doctor` checks everything and names
  each failed check; `docs/how-to/fix-doctor-checks.md` has a section per
  check.
- `sudo pinka status` shows the units, containers, Incus instances, GPU
  and last backup; the units log to the journal (`journalctl -u 'pinka-*'`; the active
  platform's units are named `<platform>-<service>`).
- `docs/operations.md` maps every day-to-day task to its guide.

## Development

Requirements: bash, curl or wget, `tar` and `sha256sum`; Node.js at the
version in `.node-version`; a Chromium or Chrome binary for Mermaid
validation (`PUPPETEER_EXECUTABLE_PATH`); and network access to PyPI, npm and
GitHub. [uv](https://docs.astral.sh/uv/) is optional: `make setup` uses the
one on `PATH` when it is the version pinned in `versions.lock.yml` and
installs that version into `build/tools/` otherwise.

```bash
make setup      # install pinned tools into .venv, node_modules and build/tools (user space)
make lint       # linters, docs lint, Mermaid validation, privacy scan
make test       # unit tests
make docs       # drift check, docs coverage check and strict documentation build
make generate   # rewrite generated files after changing their sources
```

`make lint`, `make test` and `make docs` are quiet: each runs its steps one by
one and prints a single line with the counts of passed, failed and skipped
items and of warnings, plus where the step logs are (`build/gate/<target>/`).
When a step fails, its complete output comes first (pytest with
`--tb=long`), and every other step still runs. `VERBOSE=1` prints everything
as the steps run, as CI does.

### What `make setup` downloads

Everything `make setup` fetches is pinned, and nothing is used before it is
verified; it changes nothing outside the checkout (no `sudo`).

| What | From | Verified by |
| --- | --- | --- |
| uv, when the one on `PATH` is not the pinned version (or there is none) | GitHub release of `astral-sh/uv` (`binaries.uv` of `versions.lock.yml`) into `build/tools/` | its sha256 from the lock, before it is unpacked (bootstrap's own `install_uv`) |
| CPython 3.12, when the machine has none | python-build-standalone's GitHub releases, through the pinned uv | uv, against the checksum in its own download list |
| The Python development tools (`.venv`) | PyPI | `uv sync --frozen`: every package's hash in `uv.lock` |
| The Node.js tools (`node_modules`) | the npm registry | `npm ci`: every package's integrity hash in `package-lock.json` |
| OPA | GitHub release (`binaries.opa`) into `build/tools/` | its sha256 from the lock |
| The Ansible collections for linting (`.ansible-collections`) | Ansible Galaxy, at the versions of `ansible/requirements.yml` (asked from Galaxy's API the way `ansible-galaxy` does, by `tools/lockcheck/pinka_lockcheck/lockcollections.py`) | each artifact's sha256 against Galaxy's, then its sha256 and size against its pin in `ansible_collections.artifacts` of the lock (an artifact without a verified pin is reported as unpinned), then the artifact checked like bootstrap's (`tools/lockcheck/pinka_lockcheck/artifact.py`: `MANIFEST.json`, `FILES.json`, only relative symbolic links inside the collection) before an offline install, then `ansible-galaxy collection verify --offline`: every file against the collection's `FILES.json`, and the locked version |
| The same collections when Galaxy is unreachable | a published release package (`make setup COLLECTIONS_PACKAGE=<file or https URL>`): its `release/collections/` | the same pins, which must all be verified, and the same checks |

Setup verifies the installed collections every time and installs them again
when anything differs. A transport error (no connection, a timeout, a
connection that broke off, HTTP 408, 429 or 5xx) or a malformed answer from
Galaxy is tried again, up to three attempts 5 and 15 seconds apart, and every
attempt is logged; any other failed download stops setup at once, and so
does a checksum mismatch, with the expected and the actual value. Nothing
unverified is installed. Without
Galaxy and without `COLLECTIONS_PACKAGE`, setup stops and says so; from a
release package, every collection needs a verified pin, and there is no
other source. Bootstrap installs the artifacts pinned in
`ansible_collections.artifacts`, from Galaxy or, when it runs from a release
package, from the package
(see [How bootstrap works](docs/explanation/bootstrap.md) and
[How to install from a release package](docs/how-to/install-from-a-release-package.md)).

The policy tests need that OPA and the agent environment tests that uv.
Outside CI these tests are skipped without them; in CI a skipped uv test fails
the job.

To check whether a machine can host the lab without changing anything on it,
run `./preflight/pinka-preflight --no-write` (see
`docs/how-to/check-a-host.md`).

None of these targets changes the host. Provisioning and role tests run only
when invoked explicitly and never in CI.

## Privacy

Pokus is meant to be deployed and customized by anyone, so this repository
contains no personal or installation-specific data. Real deployment data
(host variables of real machines, researchers' SSH keys, installer answers,
vaults) belongs in your lab's own private fork or configuration repository and
is excluded by `.gitignore`. `make privacy` enforces this; CI can add a private
denylist through the `PINKA_PRIVACY_DENYLIST` secret, which only the `lint`
and `privacy` jobs receive. Its value is a list of terms separated by
newlines or commas, matched case-insensitively as whole words; findings
never print a term. The same variable works locally:
`PINKA_PRIVACY_DENYLIST="<terms>" make privacy`. A scan in CI without it (a
pull request from a fork gets no secrets) prints a warning. Inside a git
work tree the scan also checks every commit reachable from `HEAD`: its
message carries no `Co-Authored-By` trailer or other attribution line, no
e-mail address outside the example domains and no denylist term, and its
author and committer e-mail is a GitHub noreply address or GitHub's own; a
shallow clone fails because its history cannot be checked. How to commit is
in [CONTRIBUTING.md](CONTRIBUTING.md).
